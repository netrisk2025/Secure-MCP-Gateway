The SRS asks to install and run the acceptance suite on a GitHub-hosted Ubuntu runner in the Enforced profile and on a macOS arm64 host in the Standalone profile, and to confirm that both installations reach their expected health state. The expected states: Enforced, not fail-closed with the release label `enforced` reported by the running Gateway (`healthy`, or `degraded` for a non-critical cause); Standalone, `degraded` with the cause `unconfined` (FR-13.10).

## Ubuntu runner, Enforced profile (CI run 39060379034 of main `771cadc`, 2026-10-17)

Installation, job `linux-integration` (`scripts/ci-integration.sh`, `scripts/ci-systemd.sh`):

- `smcpctl runtime doctor`: `enforced profile: all prerequisites present` (systemd, rootless Podman on cgroup v2, nftables, AppArmor; the AppArmor profile was loaded by the installer step that follows).
- `packaging/linux/install-enforced.sh` twice: the first run created `smcpd.service`, `smcp-nftables.service`, the `smcp-srv` drop-in and the AppArmor profiles `smcpd` and `smcp-server` (enforce); the second run reported each as `present`.
- An enforced instance started by hand: `health: degraded; causes: unverified_manifests; release label: enforced`; the reference server ran in the sandbox, the probe could not open network sockets or write outside its grant, and a server with `network = "egress"` reached only its Egress Broker.
- `smcpctl install --profile enforced` (19:00:53Z): `created started smcpd.service`, `health: healthy`; a second run changed nothing. With the sandbox probe, a policy and a vault added: `health: degraded; causes: unverified_manifests; release label: enforced`, `smcpd.service main PID 12739, user smcp-core`, a tool call through the sandbox, server processes under `smcp-srv`'s subordinate UIDs.

Acceptance suite, job `acceptance-enforced` (`SMCP_ACCEPTANCE_PROFILE=enforced go test -run TestAT ./internal/acceptance/`): every scenario reported `SCENARIO: AT-nn profile=enforced`; AT-01 to AT-06, AT-09, AT-10, AT-13 to AT-16 and AT-18 to AT-21 passed (16), AT-17 skipped (it runs in the `offline` job). Artifact `acceptance-enforced-results`.

## macOS arm64, Standalone profile

Installation, job `install-standalone (macos-latest)` of the same CI run (image `macos-26-arm64`, `scripts/ci-install-standalone.sh`): `smcpctl install` created the state directory, keys and TLS certificates and the launchd agent `com.smcp.gateway` (loaded), then reported `health: degraded` (cause `unconfined`, servers run as the user); the service manager ran `smcpd`; a second `smcpctl install` changed nothing; `smcpctl uninstall` kept the journal.

Acceptance suite, on a workstation (macOS 26.6.2, darwin/arm64, Go 1.26.1), 2026-10-17, finished 19:32:49Z: `TMPDIR=<scratch> go test -count=1 -v -timeout 25m -run TestAT ./internal/acceptance/`. Every scenario reported `profile=standalone`; AT-01 to AT-06, AT-09, AT-10, AT-13 to AT-16 and AT-18 to AT-21 passed (16), AT-17 skipped; `ok ... internal/acceptance 90.746s`.

## Deviations

- The acceptance suite bootstraps its own Gateway instances; it did not run against the service that `smcpctl install` created in the same job. Installation and suite ran on the same platform image (Ubuntu) or the same platform (macOS arm64) as separate steps.
- The macOS suite ran from branch `docs/verification-records`, whose differences from `771cadc` at that time were in `tools/reqreport`, the CI workflow files, the reference package recipes, `scripts/itest-client` (a `-repeat` flag), the `smcpctl approvals show` anomaly line and documentation; none is used by `internal/acceptance`.
- The scenarios that `internal/acceptance` does not contain (AT-07, AT-08, AT-11, AT-12, AT-17) run in other jobs and are not part of this demonstration.
