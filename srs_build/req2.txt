### FR-3 Policy administration, decision and approval

@FR-3 | Policy capability
P: —
S: The Gateway SHALL author, validate, simulate, publish and evaluate immutable policy revisions and SHALL manage human approvals required by them.
A: E-05; E-06; E-07; F-10; F-11; F-12; F-13; F-14; F-15; F-16; F-17; F-18
V: Analysis | Review the verification results of every FR-3 child requirement; confirm each has passed.
SRC: ARCH §4 SS-3; ARCH §7
R: Developing and testing policy is the owner's primary research purpose.

@FR-3.1 | Policy object types
P: FR-3
S: The Gateway SHALL support the policy object types Framework Profile and Session Allow Policy Template in the signed policy document of the Policy Administration Service (E-05), Secret Use Policy in the Secret Broker (E-20), Audit Profile, Observation Policy and Anomaly Response Policy as published observation objects of the Management Console & Control API (E-24), and Research Campaign in the Research Dataset Service (E-32), each validated before it takes effect and kept under a revision or object identifier.
A: E-05; E-20; E-24; E-32; F-10; I-06; I-07; D-01
V: Test | Create, validate and publish or activate one object of each type; confirm each is stored under its identifier and evaluated by its element.
SRC: ARCH §7.2; OWNER (release 1.0 object homes)
R: These objects compose the Allow-policy model. Release 1.0 keeps each object with the element that evaluates it rather than in one document: the policy document holds what the decision path evaluates, and secret-use, observation and research objects are validated and versioned by their own services with their own control API routes and roles (Appendix C). Response Policy and Runtime Profile objects are deferred (FR-3.26).

@FR-3.26 | Response Policy and Runtime Profile objects
P: FR-3
S: The Policy Administration Service (E-05) SHALL support Response Policy and Runtime Profile objects as published, versioned policy objects.
A: E-05; E-11; E-15; F-10; I-06; D-01
V: Test | Create, validate and publish one Response Policy and one Runtime Profile; confirm each is stored and evaluated by E-11 and E-15.
SRC: ARCH §7.2
R: Separately published response and runtime objects let a policy author change response handling and instance limits without editing configuration.
DEFER: Release 1.0 sets response handling with the `filters` obligations of permit rules and the `[filters]` configuration (where a requirement names the Response Policy, release 1.0 reads that configuration), and runtime limits with the verified manifest and the `[runtime]` configuration. Instance scopes that would need a Runtime Profile are already deferred (FR-5.10). Separate Response Policy and Runtime Profile objects need a publication path, schema and simulation support that release 1.0 does not have.

@FR-3.2 | Policy schema
P: FR-3
S: The Policy Administration Service (E-05) SHALL validate every policy object against a versioned JSON Schema for its type before storing it.
A: E-05; F-10; I-07
V: Test | Submit objects with a missing field, a wrong type and an unknown enumeration value; confirm each is rejected with a field-level message.
SRC: ARCH §4 E-05; SEC 7.3
R: Typed records make evaluation deterministic.

@FR-3.3 | Draft workspace
P: FR-3
S: The Policy Administration Service (E-05) SHALL hold edits in a named draft derived from a stated parent revision until the draft is published or discarded.
A: E-05; F-10; I-06
V: Demonstration | Create a draft, edit it in two sessions of G-02, discard one and publish the other; confirm the active revision changes only on publish.
SRC: ARCH §4 E-05
R: Authors iterate on policy without affecting enforcement.
DEFER: Release 1.0 has no server-side named drafts. A document is validated and simulated through the control API without being stored, and published with a stated parent revision that must still be active (a stale parent is refused, so two editors cannot overwrite each other); the G-02 editor keeps the unpublished text in the browser. Named drafts shared between sessions are deferred.

@FR-3.4 | Revision record
P: FR-3
S: The Policy Administration Service (E-05) SHALL record for each published revision its ID, parent revision ID, content digest, policy-schema version, evaluator version, publishing actor, publication time, simulation result reference and policy-signing key ID.
A: E-05; F-12; D-01
V: Inspection | Publish a revision; inspect the record in the Policy Store for each field.
SRC: A2 §4.1 PolicyRevision; SEC 1.14
R: Supports reproducible research and audit linkage.

@FR-3.5 | Policy simulation
P: FR-3
S: The Policy Administration Service (E-05) SHALL evaluate a draft against a stored fixture set and report, per fixture, the decision under the draft, the decision under the active revision and the difference.
A: E-05; F-11; I-06
V: Test | Run a 50-fixture set against a draft that removes one grant; confirm exactly the affected fixtures report a changed decision.
SRC: ARCH §4 E-05; ARCH §11 item 8
R: Authors must see the effect of a change before publishing it.

@FR-3.6 | Effective permission report
P: FR-3
S: The Policy Administration Service (E-05) SHALL produce, for a selected principal and template, the list of tools and argument constraints the draft or active revision permits.
A: E-05; F-11; I-06
V: Test | Generate the report for a fixture principal; compare against hand-computed expected permissions.
SRC: A2 §7.2 (Effective tools by principal)
R: Makes the tailored Allow policy reviewable.

@FR-3.7 | Observation cost estimate
P: FR-3
S: The Policy Administration Service (E-05) SHALL estimate records per day, storage per day and added p95 latency for a draft Observation Policy or Research Campaign from the trailing 7 days of call rates.
A: E-05; F-66; I-06
V: Test | Estimate a policy over a replayed 7-day fixture traffic set; confirm estimates are within ±25% of the measured values after one replayed day.
SRC: ARCH §11 item 6; ARCH §5 F-66
R: Researchers must know the cost of a capture choice before publishing it.
DEFER: Release 1.0 reports the measured cost of observation instead of an estimate: GET /api/v1/observations/cost ranks the time spent per stage, policy revision and Observation Policy from recorded spans, and the meta-metrics give records and store growth per interval. A forecast for a draft Observation Policy or Research Campaign from seven days of call rates is deferred until those object types have drafts (FR-3.3).

@FR-3.8 | Policy export and import

A: E-05; F-10; I-06
V: Test | Export a revision, import it into a clean instance and publish; confirm identical decisions over the fixture set.
SRC: OWNER (policy development and research reproducibility)
R: Policies are the research artifact and must be portable.

@FR-3.9 | Policy rollback
P: FR-3
S: The Policy Administration Service (E-05) SHALL roll back by publishing the content of a selected earlier revision as a new revision.
A: E-05; F-12; I-06
V: Test | Roll back to revision N-2; confirm a new revision ID with N-2 content becomes active.
SRC: ARCH §4 E-05; SEC 7.9
R: Rollback keeps history linear and immutable.

@FR-3.10 | Compiled decision snapshot
P: FR-3
S: The Policy Decision Service (E-06) SHALL compile the active revision into an in-memory decision snapshot when the revision is activated, and SHALL evaluate requests against that snapshot.
A: E-06; F-13; I-07
V: Test | Activate a revision; stop the graph database and the Observation Store; confirm decisions continue unchanged for 60 seconds with no Data Server access per decision.
SRC: ARCH §15 E-05/E-06; ARCH §14
R: Decision latency must not depend on a database round-trip.

@FR-3.11 | Decision record
P: FR-3
S: The Policy Decision Service (E-06) SHALL return for each evaluation a decision ID, outcome, reason code, considered, applicable and decisive rule IDs, effective obligations, selected route, policy revision ID, baseline snapshot ID and evaluation duration.

V: Test | Evaluate permit, deny and default-deny fixtures; confirm all fields are present and correct.
SRC: A2 §4.1 Decision; SEC 1.19

@FR-3.12 | Obligation types
P: FR-3
S: The Policy Decision Service (E-06) SHALL express obligations using the types request filters, response filters, approval, audit profile, observation policy, rate limit, size limit, timeout, egress grants, secret grants, runtime profile and anomaly response.

V: Test | Evaluate a fixture rule carrying every obligation type; confirm each appears in the decision.
SRC: ARCH §4 E-06; ARCH §7.2
R: Enforcement elements consume a closed set of obligation types.

@FR-3.13 | Rate limit counters
P: FR-3
S: The Policy Decision Service (E-06) SHALL maintain sliding-window call counters per principal, per session and per tool, and SHALL apply the smallest applicable rate bound, with CP-11 as the default principal bound.
A: E-06; F-14; I-08
V: Test | Exceed a session limit lower than the principal limit; confirm -31005 at the session bound.
SRC: SEC Appendix A (principal tool rate); SEC Appendix F (resource limits)
R: Rate limits are a policy obligation.

@FR-3.14 | Approval request creation
P: FR-3
S: When a decision carries an approval obligation and no matching unconsumed approval exists, the Approval Service (E-07) SHALL create a pending approval record bound per SR-1.18-2, notify approvers (FR-3.23) and hold the call (FR-3.19).
A: E-07; E-02; F-17; I-10; X-01
V: Test | Call a tool that requires approval; confirm a pending record visible in G-13 and in `smcpctl approvals list`, a desktop notification through the test notifier, and that the call is held rather than answered.
SRC: ARCH §4 E-07; SEC 1.18; OWNER (approvals: hold mode)
R: Approval is out-of-band. Holding the call lets an approved call finish in the same turn of the agent; the retry path remains for calls that outlast the hold.

@FR-3.15 | Approval consumption on retry
P: FR-3
S: When a session retries a call whose canonical arguments digest matches an approved, unexpired, unconsumed approval for that session, the Approval Service (E-07) SHALL mark the approval consumed and permit dispatch to proceed.
A: E-07; F-18; I-10
V: Test | Approve a pending request and retry the identical call; confirm dispatch, and confirm a second retry is denied.
SRC: ARCH §4 E-07; SEC 1.18
R: One-use approval bound to the exact request.

@FR-3.16 | Approval status query
P: FR-3
S: The Approval Service (E-07) SHALL report the state `pending`, `approved`, `denied`, `expired` or `consumed` of an approval through `GET /smcp/v1/approvals/{id}` to the session that created it.
A: E-07; F-18; X-01
V: Test | Query an approval from the creating session and from another session; confirm the state and a 404 for the other session.
SRC: ARCH §4 E-07
R: Harness adapters need to know when to retry.

@FR-3.17 | Approver decision
P: FR-3
S: The Approval Service (E-07) SHALL record each approve or deny decision with approver identity, decision time and an optional comment.

@FR-3.18 | Approval evidence display

SRC: ARCH §4 E-07; ARCH §9.6

@FR-3.19 | Approval hold mode
P: FR-3
S: While an approval-obligated call is pending, the Approval Service (E-07) SHALL keep the call parked for at most the CP-45 hold bound, and the Protocol Mediator (E-02) SHALL send a keep-alive every CP-45 keep-alive interval: a `notifications/progress` message when the request carries a progress token, and an SSE comment line otherwise.
A: E-07; E-02; F-17; X-01
V: Test | Call an approval-obligated tool with and without a progress token and leave it pending; confirm keep-alives at the interval in both forms and no response before the hold bound.
SRC: OWNER (approvals: hold mode with progress keep-alives); MCP:basic/utilities/progress
R: Harnesses close idle requests. Keep-alives hold the call open while a person decides.

@FR-3.20 | Approval during hold
P: FR-3
S: When a held call's approval is granted before the CP-45 hold bound, the Approval Service (E-07) SHALL consume the approval and continue the same call to launch authorization (F-29), so that the harness receives the tool result as the response to its original request.
A: E-07; E-12; F-18; F-17; I-10; I-11
V: Test | Hold a call; approve it from G-13; confirm the original request returns the tool result, the approval is `consumed`, and a second identical call creates a new approval.
SRC: OWNER (approvals: hold mode)
R: The agent's turn completes without a retry when the person answers in time.

@FR-3.21 | Denial during hold
P: FR-3
S: When a held call's approval is denied, the Approval Service (E-07) SHALL end the call with Gateway error `-31001` and reason code `APPROVAL_DENIED`.
A: E-07; E-02; F-18; X-01
V: Test | Hold a call; deny it; confirm `-31001` with `APPROVAL_DENIED` and no dispatch event.
SRC: OWNER (approvals: approve or deny)
R: A denial is a policy outcome and is reported as one.

@FR-3.22 | Hold bound fallback
P: FR-3
S: When a held call reaches the CP-45 hold bound without a decision, the Protocol Mediator (E-02) SHALL end the call with Gateway error `-31002` carrying `data.approvalId`, `data.expiresAt`, the plain-language `data.message` and `data.approvalUrl` (FR-1.51), and the Approval Service (E-07) SHALL keep the approval pending until its CP-17 expiry so that a retry after approval consumes it (FR-3.15).
A: E-07; E-02; F-17; X-01
V: Test | Hold a call past the bound; confirm the `-31002` data members; approve; retry the identical call; confirm dispatch.
SRC: OWNER (approvals: fallback to -31002 with plain-language retry text and a console deep link)
R: The hold is bounded so a harness never waits indefinitely; the approval survives the fallback.

@FR-3.23 | Approver notification
P: FR-3
S: Within 2 seconds of creating a pending approval, the Approval Service (E-07) SHALL notify approvers in the Approvals view (G-13), in the `smcpctl approvals watch` stream and through an OS desktop notification (X-14) whose text contains only the public tool name, the server alias, the approval ID and the console URL.
A: E-07; E-24; F-17; X-05; X-14
V: Test | Create an approval with the test notifier attached; confirm the three notices within 2 seconds and that the desktop notification text contains no argument value; remove the notifier binary and confirm the approval flow is unaffected and a diagnostic log warning is written.
SRC: OWNER (approvals: console, CLI and OS desktop notification)
R: A held call is only useful if a person learns about it while the hold lasts. Arguments stay out of OS notifications because notification centers persist and display them outside the Gateway's control.

@FR-3.24 | Approval CLI
P: FR-3
S: The `smcpctl approvals` command SHALL provide `list`, `show`, `approve`, `deny` and `watch` subcommands that authenticate to the control API as a person holding the Approver or Administrator role and display the FR-3.18 evidence before an approve or deny takes effect.
A: E-24; E-07; F-18; X-05
V: Test | Approve and deny held calls with the CLI as an Approver; confirm the evidence is printed, the decisions are recorded with the approver identity, and an Auditor account is refused.
SRC: OWNER (approve and deny via smcpctl approvals)
R: Operators who work in a terminal need an approval path that does not require the browser.

@FR-3.25 | Real-harness approval acceptance
P: FR-3
S: The Gateway project SHALL verify the approval flow end to end with Claude Code at its Appendix K pinned version, covering a held call approved from G-13, a held call approved with `smcpctl approvals`, a denied call and a call that reaches the hold bound, and SHALL record the harness-visible text of each outcome.
A: E-07; E-02; E-24; F-17; F-18; X-01; X-05
V: Demonstration | Run the four cases with the pinned Claude Code build against a Gateway at the release commit; confirm each outcome and file the recorded transcript in `docs/verification/`.
SRC: REVIEW (C5)
R: Hold mode depends on harness timeout and progress behavior that unit tests cannot show.

### FR-4 Enforcement pipeline

@FR-4 | Enforcement pipeline
P: —
S: The Gateway SHALL process each tool call through ordered access-time, run-time and response-time enforcement stages.
A: E-08; E-09; E-10; E-11; E-12
V: Analysis | Review the verification results of every FR-4 child requirement; confirm each has passed.
SRC: ARCH §2.1 item 4; ARCH §4 SS-4; ARCH §18.3
R: The owner's three control points.

@FR-4.1 | Canonical request object
P: FR-4
S: The Protocol Mediator (E-02) SHALL convert each `tools/call` into a canonical request containing correlation ID, session ID, principal ID, public tool name, resolved server and tool revision IDs, canonicalized arguments, argument digest and receipt time.
A: E-02; E-08; F-02; I-03
V: Test | Submit equivalent calls differing only in JSON key order and whitespace; confirm identical argument digests.
SRC: ARCH §4 E-02; A2 §4.2 step 1
R: Policy, approval and audit bind to one canonical form.

@FR-4.2 | Correlation ID
P: FR-4
S: The Protocol Mediator (E-02) SHALL assign each northbound request a UUIDv7 correlation ID that every element attaches to the records and events it produces for that request.
A: E-02; F-02; I-29; I-18
V: Test | Trace one call through audit, observation and span records; confirm all share the correlation ID.
SRC: ARCH §10.4; A2 §5
R: Joins records across elements.

@FR-4.3 | Stage order
P: FR-4
S: The Access Enforcement Point (E-08) SHALL execute the stages authenticate, session check, decision, request inspection, request scoring, approval, launch authorization, dispatch, response validation, response inspection, response scoring and release authorization in that order.
A: E-08; E-09; E-10; E-11; E-12; F-20; F-21; F-29; F-30
V: Test | Instrument a call and record stage-entry times; confirm the order.
SRC: ARCH §18.3
R: Each stage depends on the results of the previous ones.

@FR-4.4 | Filter interface
P: FR-4
S: The Request Inspection Pipeline (E-09) and the Response Inspection Pipeline (E-11) SHALL execute filters through one versioned filter interface returning `pass`, `transform` or `block` with findings, timing and filter version.

V: Inspection | Inspect the filter interface definition and the registered filters; confirm every filter implements it.
SRC: ARCH §4 E-09; ARCH §4 E-11
R: Researchers add and compare filters without changing the pipeline.

@FR-4.5 | Built-in request filters
P: FR-4
S: The Request Inspection Pipeline (E-09) SHALL provide the request filters `schema-validate`, `path-canonicalize`, `url-canonicalize`, `size-limit`, `secret-fingerprint`, `injection-detect` and `unicode-control`.
A: E-09; F-21
V: Test | Run each filter against its positive and negative fixture corpus; confirm the expected disposition for each fixture.
SRC: ARCH §4 E-09
R: The baseline request controls.

@FR-4.6 | Built-in response filters
P: FR-4
S: The Response Inspection Pipeline (E-11) SHALL provide the response filters `output-schema`, `secret-fingerprint`, `pii-detect`, `injection-marker`, `unicode-control`, `content-type-gate` and `size-limit`.
A: E-11; F-27
V: Test | Run each filter against its positive and negative fixture corpus; confirm the expected disposition for each fixture.
SRC: ARCH §4 E-11
R: The baseline response controls.

@FR-4.7 | Filter findings
P: FR-4
S: The Request Inspection Pipeline (E-09) and the Response Inspection Pipeline (E-11) SHALL emit each filter's findings and duration to the Observation Collector (E-29).

V: Test | Trigger an `injection-detect` finding; confirm an observation record with the filter ID, finding and duration.

@FR-4.8 | Dispatch queue
P: FR-4
S: The Tool Dispatcher (E-10) SHALL enforce the CP-10 per-principal and total concurrency limits using a bounded FIFO waiting queue and SHALL reject calls arriving at a full queue with Gateway error `-31005`.

@FR-4.9 | Upstream execution timeout

@FR-4.10 | Response buffering

@FR-4.11 | Release disposition

@FR-4.12 | Provenance metadata

@FR-4.13 | Launch capability

V: Test | Attempt dispatch with no capability, a used capability and a capability from another call; confirm each is refused.

@FR-4.14 | Emergency stop control
P: FR-4

A: E-12; F-31; I-06
V: Test | Stop, attempt calls, then resume as a non-administrator and as an administrator; confirm the state transitions.
SRC: ARCH §4 E-12; SEC 7.6

@FR-4.15 | Synchronous scoring integration
P: FR-4
S: When the Observation Policy selects synchronous scoring, the Request Inspection Pipeline (E-09) and the Response Inspection Pipeline (E-11) SHALL obtain the anomaly band from the Anomaly Scorer (E-31) before launch authorization and before release authorization respectively.
A: E-09; E-11; E-31; F-21; F-27; F-88; F-89; I-31
V: Test | Enable synchronous scoring; confirm that an abnormal fixture's obligations apply before dispatch and before release.
SRC: ARCH §9.5 (Scoring mode); ARCH §18.3
R: Anomaly obligations must act at the control points.

@FR-4.16 | Versioned detection rule sets
P: FR-4
S: The Request Inspection Pipeline (E-09) and the Response Inspection Pipeline (E-11) SHALL load the rules of the `secret-fingerprint`, `injection-detect`, `injection-marker`, `pii-detect` and `unicode-control` filters and of the metadata scan from versioned rule-set files, each with an ID, version and SHA-256 digest, and SHALL record the rule-set ID and version in every finding.
A: E-09; E-11; E-14; F-21; F-27; F-34
V: Test | Load two versions of a rule set; run the same input under each; confirm the findings name the version in effect and that a rule-set file whose digest does not match its index is refused at load.
SRC: REVIEW (I1); SEC 5.14

@FR-4.17 | Injection findings as tags
P: FR-4
S: The `injection-detect` and `injection-marker` filters SHALL record each finding as a provenance tag on the released result and as observation parameters P-043 and P-143, and SHALL leave the release disposition unchanged.
A: E-09; E-11; F-21; F-27; F-28
V: Test | Run the injection corpus through both filters; confirm every positive sample yields a tag and parameter value and that each result is released with the same disposition as without the filter.
SRC: OWNER (injection-marker tags only in v1); REVIEW (I1)
R: Prompt-injection detection has false positives and false negatives that are not yet measured well enough to block on. Tags give the agent and the researcher the signal without claiming a control.

@FR-4.18 | Untrusted-content delimiting
P: FR-4
S: When the Response Policy carries the `delimit-untrusted` obligation, the Response Inspection Pipeline (E-11) SHALL enclose each text content item from a tool whose manifest `source_trust` is `untrusted` between delimiter lines that carry a per-response random nonce of at least 96 bits, and SHALL remove from the enclosed text any line matching the delimiter pattern.
A: E-11; F-27; F-28
V: Test | Enable the obligation; return text containing a forged delimiter line from an untrusted-source fixture; confirm the released text is enclosed with a fresh nonce and the forged line is removed.
SRC: REVIEW (I2)
R: An optional, deterministic way to mark where untrusted text begins and ends for agents that honor it. It is not a control on its own.

### FR-5 Server trust, runtime and southbound MCP client

@FR-5 | Server trust and execution

S: The Gateway SHALL import verified server packages from the Trusted MCP Server Library and SHALL run them as contained local MCP servers reached through a Gateway MCP client.

V: Analysis | Review the verification results of every FR-5 child requirement; confirm each has passed.
SRC: ARCH §2.1 item 1; ARCH §4 SS-5
R: Hosting curated, signed servers locally is the core vision.

@FR-5.1 | Library sources

V: Test | Import a package from the directory library; confirm it succeeds.

@FR-5.3 | Library polling

@FR-5.16 | Era probe

The `server/discover` probe and modern southbound requests are deferred to the release that adds the modern southbound client. @FR-5.33 | Runtime observables
P: FR-5
S: The Runtime Monitor (E-17) SHALL collect, per instance, process creations, memory peak, CPU time and OOM or limit events.

V: Test | Run a fixture performing each behavior; confirm each event is collected.

File opens outside the declared mounts and network connection attempts are not observed: they need privileged tracing (fanotify or eBPF) that the rootless Enforced profile does not have. They are prevented instead: an instance sees only its granted mounts (SR-4.6-1) and reaches only its Egress Broker endpoints (SR-4.5-1), and the broker records every operation (FR-5.36).

@FR-5.35 | Containment actions
