### FR-6 Secrets

@FR-6 | Secret management
P: —
S: The Gateway SHALL store server secrets and deliver each secret only through a policy-selected delivery mode for an authorized use.
A: E-19; E-20; F-47; F-48; F-49; F-50; F-51; F-52
V: Analysis | Review the verification results of every FR-6 child requirement; confirm each has passed.
SRC: ARCH §2.1 item 5; ARCH §8
R: Managed secrets are an owner capability.

@FR-6.1 | Secret record
P: FR-6
S: The Secret Vault (E-19) SHALL store for each secret a reference ID, name, type, version, owner, creation time, rotation time, expiry and the encrypted value.
A: E-19; F-47; D-04
V: Inspection | Create a secret through G-12; inspect the stored record and confirm the value field is ciphertext.
SRC: ARCH §4 E-19
R: Secrets need versioned, attributable records.

@FR-6.2 | Write-only values
P: FR-6
S: The Secret Vault (E-19) SHALL accept secret values on create and rotate operations and SHALL return only metadata on every read operation.
A: E-19; F-47; X-08; I-06
V: Test | Call every secret read operation of the control API; confirm no value or ciphertext is returned.
SRC: ARCH §4 E-19; SEC 8.5
R: Values can be written but never read back.

@FR-6.3 | Rotation
P: FR-6
S: The Secret Vault (E-19) SHALL rotate a secret by creating a new version, keeping the previous version deliverable for at most the CP-15 overlap, and then retiring it.
A: E-19; F-48
V: Test | Rotate a secret; confirm delivery of the new version and that the old version stops at the overlap limit.
SRC: ARCH §4 E-19; SEC Appendix A
R: Rotation without downtime.

@FR-6.4 | Retirement zeroization
P: FR-6
S: When a secret version is retired, the Secret Vault (E-19) SHALL delete its ciphertext and record a retirement event.
A: E-19; F-48; I-18
V: Test | Retire a version; confirm the ciphertext is absent from the store and a retirement event exists.
SRC: ARCH §4 E-19
R: Retired material must not remain recoverable from the vault.

@FR-6.5 | Secret slot binding
P: FR-6
S: A secret SHALL be bound to a server only through a Secret Use Policy naming a declared secret slot, the permitted tools, destination, delivery mode, purpose, rate, time window and approval requirement, and the Policy Administration Service (E-05) SHALL show each binding in the effective permission report.
A: E-05; F-10; D-01
V: Test | Publish a Secret Use Policy for a declared slot; confirm the binding appears in the effective permission report.
SRC: ARCH §7.2 Secret Use Policy
R: Secret use is governed by policy. Release 1.0 declares secret slots in the Secret Use Policy document (or as `secret_env` entries of the server configuration); the secret slots of a signed manifest (Appendix J) are recorded with the package but not read by the Secret Broker.

@FR-6.6 | Delivery mode S1
P: FR-6
S: For delivery mode S1, the Secret Broker (E-20) SHALL pass the secret to the Egress Broker (E-18), which SHALL insert it into the header template declared by the slot on each authorized request to the bound destination.
A: E-20; E-18; F-50; F-46; I-26
V: Test | Call a fixture API through S1; confirm the destination receives the header and the instance environment, memory dump and mounts lack the value.
SRC: ARCH §8.2 S1
R: The preferred mode keeps the secret outside the sandbox.

@FR-6.7 | Delivery mode S2
P: FR-6
S: For delivery mode S2, the Secret Broker (E-20) SHALL write the secret to a per-call file in an instance-private tmpfs mount before dispatch and SHALL delete the file when the call completes.
A: E-20; F-50; F-52; I-28
V: Test | Call an S2 fixture; confirm the file exists during the call and not after.
SRC: ARCH §8.2 S2
R: Short exposure for protocols the broker cannot proxy.

@FR-6.8 | Delivery mode S3
P: FR-6
S: For delivery mode S3, the Secret Broker (E-20) SHALL write the secret to an instance-private tmpfs file at instance launch and SHALL delete it at instance teardown.
A: E-20; F-50; F-52; I-28
V: Test | Launch and tear down an S3 instance; confirm the file lifetime.
SRC: ARCH §8.2 S3
R: Long-lived connections need instance-lifetime secrets.

@FR-6.9 | Delivery mode S4
P: FR-6
S: The Secret Broker (E-20) SHALL deliver a secret through a launch environment variable only when the secret slot declares no other mode and the Secret Use Policy carries an approved S4 waiver.
A: E-20; E-05; F-50; F-10
V: Test | Attempt S4 with and without a waiver and with another supported mode; confirm only the waiver-without-alternative case is accepted.
SRC: ARCH §8.2 S4
R: Environment delivery is the most exposing mode. Release 1.0 declares secret slots in the Secret Use Policy document (or as `secret_env` entries of the server configuration); the secret slots of a signed manifest (Appendix J) are recorded with the package but not read by the Secret Broker.

@FR-6.10 | Leak fingerprints
P: FR-6
S: The Secret Broker (E-20) SHALL derive keyed HMAC-SHA-256 fingerprints over each delivered secret's full value and every 12-character substring of its raw, Base64, hex and URL-encoded forms, and SHALL register them with the Response Inspection Pipeline (E-11) and the Observation Collector (E-29).
A: E-20; F-51; I-14
V: Test | Deliver a secret and return it raw, Base64-encoded and as a 12-character fragment in a response; confirm each is detected.
SRC: ARCH §8.5
R: Leak detection without holding plaintext in the filters.

@FR-6.11 | Secret use event
P: FR-6
S: The Secret Broker (E-20) SHALL record each delivery and each denial with secret reference, version, slot, mode, server revision, tool, correlation ID and decision ID, and without the secret value.
A: E-20; F-49; F-50; I-18
V: Test | Deliver and deny secrets; inspect the events and search them for the value.
SRC: ARCH §4 E-20
R: Every secret use is attributable.

@FR-6.12 | Reference impact preview
P: FR-6
S: The Secret Vault (E-19) SHALL report every Secret Use Policy, server revision and slot that references a selected secret.
A: E-19; F-47; I-06
V: Test | Bind a secret in two policies; confirm both appear in the impact report.
SRC: SEC 8.5
R: Operators see the effect of rotation or revocation.

### FR-7 Audit, keys and health

@FR-7 | Assurance services
P: —
S: The Gateway SHALL record security evidence, manage its cryptographic keys and monitor the health of enforcement dependencies.
A: E-21; E-22; E-23
V: Analysis | Review the verification results of every FR-7 child requirement; confirm each has passed.
SRC: ARCH §4 SS-7
R: Assurance services support every control.

@FR-7.1 | Event schema
P: FR-7
S: The Audit & Evidence Service (E-21) SHALL record each security event with event ID, timestamp, event class, phase, origin, correlation ID, session ID, principal ID, decision ID, policy revision, server revision, tool revision, outcome, reason code and policy status.
A: E-21; F-53; I-18
V: Inspection | Inspect events of each class; confirm each field is present or explicitly null.
SRC: A2 §4.1; SEC 6.4; SEC 6.19
R: A uniform schema enables linkage and query.

@FR-7.2 | Event phases
P: FR-7
S: The Audit & Evidence Service (E-21) SHALL support the call phases `requested`, `denied`, `authorized`, `dispatched`, `completed`, `failed`, `indeterminate`, `filtered`, `delivered` and `withheld`.
A: E-21; F-53
V: Test | Drive calls to each terminal outcome; confirm the recorded phase sequence.
SRC: A2 §5
R: Observed phases, not inferred success.

@FR-7.3 | Audit query API
P: FR-7
S: The Audit & Evidence Service (E-21) SHALL answer audit queries filtered by time range, principal, session, server, tool, rule, outcome, event class and policy revision, with cursor pagination of at most 500 events per page.
A: E-21; F-57; I-06; I-30
V: Test | Run each filter over the reference dataset; confirm correct results and page bounds.
SRC: SEC 8.4
R: Investigation needs bounded, structured queries.

@FR-7.4 | Journal segment format
P: FR-7
S: The Audit & Evidence Service (E-21) SHALL write the evidence journal as JSON Lines segments closed at 1,000 events or 60 seconds, each holding the SHA-256 of the previous segment and an Ed25519 signature.
A: E-21; F-55; D-06
V: Inspection | Inspect three consecutive segments; confirm the chaining and signatures.
SRC: ARCH §4 E-21; SEC 6.12
R: Tamper evidence that is independent of the Data Server.

@FR-7.5 | Journal verification
P: FR-7
S: The `smcpctl journal verify` command SHALL validate the hash chain and the signature of every segment in a journal directory and report the first failure.
A: E-21; F-55; D-06
V: Test | Verify an intact journal and one with a modified byte; confirm a pass and a precise failure.
SRC: ARCH §4 E-21
R: Evidence must be checkable offline.

@FR-7.6 | Alerts
P: FR-7
S: The Audit & Evidence Service (E-21) SHALL raise an alert in the management console for each event matching an alert rule of the effective Audit Profile.
A: E-21; F-53; I-06
V: Test | Configure an alert on `withheld`; trigger it; confirm the console alert.
SRC: ARCH §7.2 Audit Profile
R: Operators need notification of significant events.
DEFER: The release 1.0 Audit Profile sets retention and escalation parameters only; it has no alert rules. The console raises alerts for anomaly bands (G-06) and health causes, and the evidence stream with filters (FR-8.23) follows any event class live. Alert rules in the Audit Profile are deferred.

@FR-7.7 | Local certificate authorities
P: FR-7
S: The Key & Trust Anchor Manager (E-22) SHALL operate a local certificate authority for Gateway TLS server certificates whose key is used for no other purpose, and SHALL issue from it only certificates limited to TLS server authentication.
A: E-22; F-59; F-60; D-08
V: Inspection | Inspect the CA certificate, an issued server certificate and the key inventory; confirm the CA key has one purpose and the issued certificate allows server authentication only.
SRC: ARCH §4 E-22; OWNER (mTLS Harness Profile deferred)
R: Separates client identity from server identity. Release 1.0 issues no client certificates (the mTLS Harness Profile, FR-2.14, is deferred), so the separate client CA is deferred with it (FR-7.15).

@FR-7.15 | Client certificate authority
P: FR-7
S: The Key & Trust Anchor Manager (E-22) SHALL operate a local certificate authority for harness client certificates separate from the server certificate authority.
A: E-22; F-59; F-60; D-08
V: Inspection | Inspect both CA certificates and an issued certificate of each kind; confirm separate roots.
SRC: ARCH §4 E-22
R: Separates client identity from server identity.
DEFER: Deferred with the mTLS Harness Profile (FR-2.14): release 1.0 authenticates harnesses with bearer access tokens and issues no client certificates, so a client CA would have nothing to sign.

@FR-7.8 | Key purposes
P: FR-7
S: The Gateway SHALL use a separate key for each of the purposes server CA, server TLS, policy signing, vault master, backup encryption, evidence signing, cursor protection, leak-fingerprint keying, research pseudonymization and Data Server credentials, and SHALL use no key for more than one purpose.
A: E-22; F-60; D-08
V: Inspection | Inspect the key inventory; confirm one key per purpose and no reuse.
SRC: ARCH §4 E-22
R: Compromise of one purpose must not affect others. Release 1.0 has no client CA (the mTLS Harness Profile, FR-2.14, is deferred), no MRTR state protection key (the MRTR Relay Profile, FR-5.25, is deferred) and no payload encryption (no payload is stored encrypted outside the vault and backups, which have their own keys). Backup encryption uses the operator's passphrase or age recipients, never a Gateway key. Leak-fingerprint keying (FR-6.10) is listed because it is a key purpose of its own.

@FR-7.9 | Key protection at rest
P: FR-7
S: The Key & Trust Anchor Manager (E-22) SHALL seal private keys to the host TPM 2.0 when present, store them in the user's login Keychain on macOS, and otherwise store them in files owned by the key-holding service identity with mode 0600, encrypted under an operator passphrase when the configuration sets `keys.passphrase = true`.
A: E-22; F-60; X-07; D-08
V: Test | Start on a TPM host, on macOS and on a non-TPM Linux host with and without the passphrase option; confirm the protection method in each case and that key files copied to another host are unusable where sealing or encryption applies.
SRC: ARCH §15 E-19/E-22; OWNER (platform profiles)
R: Keys must not sit in plaintext on disk where the platform offers protection. An unattended service cannot wait for a passphrase at every start, so the passphrase is an option rather than the default.
DEFER: Release 1.0 stores private keys in files with mode 0600 under the state directory, owned by the key-holding identity in the Enforced profile (SR-6.12-1); the vault master key can be held in the macOS Keychain. TPM sealing, Keychain storage of every private key and passphrase encryption are deferred: they need reference hardware and an unattended-start design that release 1.0 does not have.

@FR-7.10 | Trust anchor enrollment
P: FR-7
S: The Key & Trust Anchor Manager (E-22) SHALL enroll a curation trust anchor only after an administrator confirms its displayed fingerprint and assigns its permitted risk classes and expiry.
A: E-22; F-58; I-06
V: Demonstration | Enroll an anchor through G-10; confirm the fingerprint confirmation step and the stored scope.
SRC: ARCH §4 E-22
R: The trust root is set by a deliberate operator ceremony.

@FR-7.11 | Health checks
P: FR-7
S: The Health & Safety Monitor (E-23) SHALL evaluate once per second, as critical causes, decision-snapshot currency, Evidence Journal writability and signing lag, mandatory-audit capacity, vault availability, clock sanity and trust-anchor validity, and, as non-critical causes, graph mirror reachability, Observation Store reachability, memory degradation stage and, in the Standalone profile, `unconfined`.
A: E-23; F-61; I-32
V: Test | Fault each dependency in turn; confirm detection within 2 seconds, `fail-closed` for each critical cause and `degraded` for each non-critical cause.
SRC: ARCH §4 E-23; ARCH §2.2 A-8, A-9; OWNER (authority decoupling)
R: Enforcement depends on the policy snapshot and the journal, not on the graph or the Observation Store, whose loss degrades analytics only.

@FR-7.12 | Health states
P: FR-7
S: The Health & Safety Monitor (E-23) SHALL report the Gateway health as `healthy`, `degraded` or `fail-closed` together with the list of active causes.
A: E-23; F-61; F-62; I-06
V: Test | Induce a non-critical and a critical fault; confirm `degraded` and `fail-closed` with causes.
SRC: ARCH §4 E-23
R: Distinguishes degraded observation from unsafe enforcement.

@FR-7.13 | Fail-closed recovery
P: FR-7
S: The Health & Safety Monitor (E-23) SHALL return from `fail-closed` to `healthy` only after every critical cause has cleared for 10 consecutive seconds and, for integrity causes, after an administrator acknowledgment.
A: E-23; F-62; I-19
V: Test | Clear an availability cause and an integrity cause; confirm the automatic and the acknowledged recovery.
SRC: ARCH §4 E-23; SEC 7.3
R: Prevents flapping and requires review after integrity failures.

@FR-7.14 | Evidence export
P: FR-7
S: When evidence export is configured, the Audit & Evidence Service (E-21) SHALL copy each closed journal segment and checkpoint to the configured local export directory within 60 seconds of segment closure.
A: E-21; F-55; X-09; D-06
V: Test | Configure an export directory; close segments; confirm copies within 60 s and that the copies verify with `smcpctl journal verify`.
SRC: ARCH §6.1 X-09
R: Offline archival of evidence without a network service.

### FR-9 Data Server

@FR-9 | Data Server
P: —
S: The Gateway SHALL hold the behavior model and observation data, and mirrors of policy, registry, session and audit data, in a Data Server consisting of a graph database, a columnar Observation Store, a Data Access Service and a Data Lifecycle & Memory Manager, with no enforcement decision depending on the Data Server's availability.
A: E-25; E-26; E-27; E-28
V: Analysis | Review the verification results of every FR-9 child requirement and of FR-9.17; confirm each has passed.
SRC: ARCH §4 SS-9; ARCH §2.2 A-9; OWNER (graph database; authority decoupling)
R: The owner requires a graph database for graph views and characterization, and decided that its unavailability degrades analytics but never opens or blocks enforcement.

@FR-9.1 | Graph data model
P: FR-9
S: The Graph Database Engine (E-25) SHALL store the node labels and relationship types defined in Appendix D with a uniqueness constraint on the `id` property of every label.
A: E-25; F-70; D-01; D-02; D-05; D-07; D-10; D-11
V: Inspection | Inspect the deployed schema; confirm every Appendix D label, relationship and constraint.
SRC: A2 §4.1; ARCH §13.1
R: A defined graph model is required for code and queries.

@FR-9.2 | Schema migrations
P: FR-9
S: The Data Access Service (E-26) SHALL apply versioned, ordered schema migrations at startup and SHALL refuse to start when the database schema version is newer than the release supports.
A: E-26; F-72; I-36
V: Test | Start against an older schema and a newer schema; confirm migration and refusal respectively.
SRC: ARCH §4 E-26
R: Controlled data-model evolution.

@FR-9.3 | Typed operation catalog
P: FR-9
S: The Data Access Service (E-26) SHALL expose to other elements only the typed operations listed in its versioned operation catalog, each mapped to one fixed parameterized query template.
A: E-26; F-72; I-07; I-30; I-33; I-34; I-35; I-06
V: Inspection | Inspect the operation catalog and its templates; confirm a one-to-one mapping and no dynamic query construction.
SRC: ARCH §4 E-26; SEC 1.13
R: Fixed operations keep query cost and authority reviewable.

@FR-9.4 | Write priority classes
P: FR-9
S: The Data Access Service (E-26) SHALL order queued writes by the priority classes P0 policy and control, P1 mandatory audit, P2 observation and P3 research.
A: E-26; F-73; I-33
V: Test | Saturate the queue with P2 writes and submit a P1 write; confirm the P1 write commits first.
SRC: ARCH §4 E-26
R: Mandatory writes must not wait behind optional data.
DEFER: In release 1.0 the Data Access Service writes only the evidence mirror, from one ordered stream: the journal (P0 and P1 records are committed to the journal before the call proceeds, independent of the graph), and observation data is written to the Observation Store, not through the Data Access Service. With one write class in the queue there is nothing to order; priority classes are deferred until a second writer shares the queue.

@FR-9.5 | Observation batching
P: FR-9
S: The Data Access Service (E-26) SHALL write observation records to the Observation Store in batches of at most 1,000 records or 200 milliseconds, whichever occurs first.
A: E-26; F-73; I-37
V: Test | Generate 5,000 records per second; confirm batch sizes and maximum batch latency.
SRC: ARCH §4 E-26
R: Batching sustains ingest rate.

@FR-9.6 | Backpressure
P: FR-9
S: When the P2 write queue exceeds 80% of its capacity, the Data Access Service (E-26) SHALL signal backpressure to the Observation Collector (E-29).
A: E-26; F-74; I-33; I-38
V: Test | Stall the Observation Store; confirm the backpressure signal at 80% queue occupancy.
SRC: ARCH §4 E-26; ARCH §18.6
R: Optional capture yields before resources are exhausted.

@FR-9.13 | Storage tiering
